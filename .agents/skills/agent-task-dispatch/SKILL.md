# Agent 任务派发规范

用途：把已经明确的任务整理成 Agent 可直接执行的任务单，同时减少无意义的 token 和上下文消耗。它只规定任务单的表达方式，不替代 requirement-grill、agent-routing、model-routing、engineering-discipline 或项目自己的 Contract/ADR。

1：一级结构
使用 `1：标题`、`2：标题`、`3：标题` 这种一级编号组织任务。只在两个一级编号之间保留一个空行。同一个一级编号内部默认不留空行。

2：禁止无意义装饰
禁止用 `=====`、`-----`、连续星号、重复井号等装饰性分隔符。默认不用 `##`、`###` 这类 Markdown 标题。不要为了“看起来正式”增加符号。

3：空行规则
空行只用于分隔两个一级编号。不要出现“同一编号内部一句话、空一行、再一句话”的排版。代码块或真实数据结构内部需要换行时不受此限制。

4：代码围栏
不要把整份任务包进代码块。只有真实代码、命令、多行 JSON、配置或必须保持原样的文本才使用代码围栏。

5：压缩表达
能写成一行就不要拆成三行。例如写 `main = <SHA>`、`Branch = codex/xxx`。短列表优先用逗号；较长列表可逐行写，但默认不用项目符号。箭头只在表达真实流程或数据链时使用。

6：去重
同一约束只写一次。把重复出现的“不要改 Frozen Contract”“不要开始下一阶段”“PPTist core = 0”等合并到一个范围/冻结边界段落。不要在前后多个编号重复提醒同一件事。

7：不能为了省 token 丢精度
以下内容必须完整保留：仓库名、branch、commit SHA、文件路径、命令、字段名、Schema/Contract 版本、RPC 名、错误码、验收数字、模型名和 Reasoning 等级。节省的是装饰和重复，不是技术信息。

8：Codex 模型声明
派发 Codex 任务前先加载 `model-routing`。在任务最前面直接写 `模型：XXX` 和 `Reasoning：XXX`。Luna 默认 Max；Terra、Sol 按 `model-routing` 选择。用户明确指定时以用户要求为准。

9：任务内容顺序
默认顺序：模型（如需要）→ 基线 → 分支 → 必读材料 → 当前状态修正 → 核心目标 → 实现约束 → 测试/验收 → 冻结边界/不做 → 文档 → PR 交付。没有必要的段落直接省略，不为了凑模板保留空章节。

10：PR 交付
如果任务要求 GitHub 交付，遵循 `pr-delivery`。完整报告写进 PR Description 或顶层 comment，聊天只保留规定的一行成功/失败确认。不要在任务末尾再次重复整份验收规则。

11：发送前自查
检查是否存在装饰分隔符、无意义 Markdown 标题、一级编号内部多余空行、整份任务代码围栏、重复约束、可合并的短句。确认删掉这些内容后，任务仍然保留所有技术边界和验收标准。

12：最小格式示例
模型：GPT-5.6 Terra
Reasoning：High

1：基线
Repo：owner/repo
main = `<SHA>`
从最新 main 创建 `agent/task-branch`，Draft PR 到 main，不要 merge。

2：目标
只完成本轮明确目标。写清输入、输出和验收标准。同一编号内部不要插入多余空行。

3：范围
不要修改冻结 Contract、不要提前做下一阶段、不要扩大依赖。相同限制只在这里写一次。

4：交付
运行指定测试，commit、push、更新 PR。完整报告写进 PR；成功后聊天只回复规定的一行。
